## Changes

- **Day-Month date format options (Discussion #116):** @austempest reported the Weekly Resets column only offered US-style Month-Day formats (`Mar 13`), which doesn't match how most of the world writes dates. Added three parallel Day-Month options — `13 Mar`, `Fri 13 Mar`, `Fri 13 Mar + time` — as a second `optgroup` in the same dropdown, directly below the existing Month-Day group. `formatResetsAt()` gained matching `date-dmy` / `date-day-dmy` / `date-day-time-dmy` branches; no other logic changed since settings load/save already reads the dropdown value generically. Tested locally on Windows.

- **Taskbar stats reverted — recurring Windows taskbar-icon identity corruption, root cause not confirmed (Discussion #32 / PR #115):** originally shipped as per-percentage session/weekly icons on the Windows taskbar (main window's own button for session, a second invisible always-on window for weekly). After extended debugging of an earlier taskbar-icon corruption report, the identified cause (a periodic `setAlwaysOnTop` call hammering the main window's icon ~720x/hour) was fixed and confirmed stable over several hours of testing. The same corruption recurred on a long-running (5+ day) profile after being closed and reopened, with the earlier fix already in place — meaning either that fix wasn't sufficient, or a different, still-unidentified trigger produces the same symptom. Rather than continue shipping a feature we can't reliably explain or reproduce on demand, the feature is backed out: the icon-drawing helpers (`fillRect`, `drawCharScaled`, `drawXGlyph`, `drawTaskbarPanel`, `generateSingleTaskbarIcon`), the second invisible taskbar window and its own AppUserModelID, and the "Show taskbar stats" settings toggle are all removed. Tray icons (notification area, separate feature/code path) are unaffected.

  **Kept from that branch, as their own standalone improvements — not taskbar-specific:**
  - **Close (X, Alt+F4, "Close window") always quits the app outright**, rather than conditionally hiding to tray only when a tray icon happened to exist. Minimize is now the sole way to tuck the app away while keeping a tray icon as the way back in.
  - **Exit/Close now force-destroy every window/tray icon and hard-exit the process directly (`app.exit(0)`)**, rather than relying on the `close`/`before-quit`/`window-all-closed` event cascade to resolve correctly.
  - **`measureSettingsHeight()`** — the settings panel now sizes itself to its actual content instead of a hardcoded height, so future row additions can't clip the panel.
  - The `isAlwaysOnTop()`-check-before-reasserting fix to the periodic interval is also kept regardless of feature status — it's a legitimate reduction in unnecessary native calls independent of the icon-corruption theory that originally motivated it.

  **Documentation debt carried forward:** README/CONTRIBUTING/QUICKSTART references to "closing minimizes to tray" still need a pass to reflect the always-quits-on-close behavior — this was already true before this revert and remains outstanding.

- **Taskbar stats reintroduced as a single split-panel icon, adapted from bastionecho's PR #115 (Discussion #32):** the two-window redesign built on top of PR #115 (backed out above) turned out to have solved a legibility problem that PR #115's own approach didn't actually have. Reviewing bastionecho's original branch directly (pulled from his fork, not re-implemented from memory) showed his icon was already drawn at the full 128x128 size Windows expects taskbar icons to be handed at, split into two threshold-colored panels — session left, weekly right — on the main window's own `setIcon()`, the same pattern the tray icons already use. No second window, no separate AppUserModelID. That sidesteps the specific mechanism (a second invisible window with its own AUMID) suspected — never confirmed — as a factor in the corruption that led to the two-window backout, without reintroducing the two-window design's own complexity.

  **Directly reused from PR #115** (adapted, not reproduced verbatim — call sites, settings-integration points, and the divider-color constant's exact placement differ from his branch): the pixel-drawing helpers `fillRect`, `drawCharScaled`, `drawXGlyph`; `drawTaskbarPanel`'s per-panel threshold-color and 99%+ white-X logic; `generateTaskbarIcon`'s left/right panel split and divider line; and `measureSettingsHeight()`, which also traces back to this same PR — it was written there to stop the taskbar-stats row from clipping the settings panel, and was kept during the two-window backout as a general-purpose improvement independent of the taskbar feature. Full credit: **@bastionecho**, PR #115.

  **Not carried over:** the settings-footer GitHub repo button (unrelated scope) and the default-on setting — `showTaskbarStats` defaults **off** here, consistent with `showTrayStats` and with treating a new taskbar-icon feature as opt-in given the history above.

  Tested locally: icon renders correctly and updates live; clicking it correctly brings the main window forward and back; threshold colors and the 99%+ X glyph confirmed at both single- and double-digit percentages; "Hide from taskbar" correctly locks/hides the toggle same as the tray-stats coupling; settings persist across a full restart. Longer-running soak test (multi-hour, through many refresh cycles, plus a close/reopen cycle) in progress to specifically validate that removing the second-window/AUMID mechanism resolves the corruption seen in the two-window version — not yet fully confirmed at time of writing.

- **`--reset-aumid` CLI flag — self-service recovery for corrupted Windows taskbar-icon identity:** the AUMID-caching theory documented in `CONTRIBUTING.md` (stale Windows Shell state cached against a specific AppUserModelID, surviving reboot/icon-cache-clear/Explorer-restart) had a known diagnostic — set a brand-new, never-used AUMID and see if the icon starts working — but no way to actually apply that fix without either a new `--profile` (works, but scatters a person's real usage history across profile folders as a side effect of a diagnostic) or a code change bumping the hardcoded AUMID string (requires a release, and only fixes it once).

  `--reset-aumid` generates a fresh, guaranteed-unique identity (`com.claudeusage.widget[.profile-<name>].reset-<timestamp>`) and saves it to a small standalone `aumid-override.json` file in the target profile's `userData` directory, then exits immediately without launching the app. The next normal launch of that profile reads the override — checked via plain `fs`, not through `electron-store`, since this has to happen before the `Store` instance exists (the AUMID is set several lines earlier in `main.js` than `new Store()` is called). Respects `--profile`, same as any other flag — `--profile=work --reset-aumid` targets that profile specifically; omitting `--profile` resets the default profile's identity. Corrupt or unreadable override files fail safe back to the default identity rather than blocking startup.

  Also added: an always-logged (not `DEBUG_LOG`-gated) `[AUMID] Using AppUserModelID: ...` line on every startup, matching the existing `[Profile]` line's reasoning — lets a reset be confirmed, or a future corruption report be triaged, from terminal output alone, without needing to inspect the override file directly.

  **Confirmed against a real corrupted install, not just tested in the abstract:** the default-profile install was stuck showing Windows' generic fallback icon (not just wrong-sized — genuinely unresolvable, confirmed by directly comparing `--profile=damon` on the same machine, which showed the same symptom, against a separate `--profile=damon.downing` that had never been corrupted and worked fine throughout). `--reset-aumid` against the default profile, followed by a normal relaunch, produced the correct application icon — confirmed clean across multiple subsequent launches in the terminal log. This is the first time the AUMID-caching theory has been directly confirmed as an actual, reproducible fix, rather than a documented lead.

  **Side finding while testing, worth knowing:** `--profile` names are sanitized to `[a-zA-Z0-9_-]`, silently converting anything else (including `.`) to `_`. `--profile=damon.downing` and `--profile=damon_downing` resolve to the exact same profile. This isn't new behavior from this branch, but it caused real confusion mid-investigation — a profile referred to with a dot was actually stored (and matched) with an underscore the whole time. Documented in README's Multi-Account Support section.

- **`--whitelist-add`/`--whitelist-remove`/`--whitelist-list` CLI — self-service domain whitelist for the login-window allowlist (Issue #120):** @lorre851 reported login hanging with `[Security] Blocked login navigation to untrusted domain: https://api.workos.com/sso/authorize?...` — their org signs into claude.ai via WorkOS SSO, and `api.workos.com` isn't in `LOGIN_ALLOWED_DOMAINS` (`main.js`'s hardcoded `['claude.ai', 'accounts.google.com', 'appleid.apple.com', 'login.microsoftonline.com']`). WorkOS itself is a legitimate, well-established enterprise identity broker — the block was correct behavior against an un-recognized domain, not a false positive on a suspicious one — but there was no way for a user to self-serve past it, and every different organization's SSO setup would hit a different domain, making a purely hardcoded allowlist a permanent one-off support burden.

  New module `src/domain-whitelist.js`: a plain JSON array of strings at `<baseUserDataPath>/domain-whitelist.json`, loaded fresh each time a login window opens and combined with `LOGIN_ALLOWED_DOMAINS` for the `will-navigate` check. Two entry shapes — a bare hostname (`api.workos.com`) matches only that exact host; a `*.`-prefixed entry (`*.workos.com`) matches the bare domain and any subdomain, mirroring the existing hardcoded-list matching semantics exactly. Validation on add rejects empty/malformed input, more than one `*`, `*` anywhere but a single leading position, and single-label hostnames (e.g. `localhost`) — and separately declines (without erroring) anything already covered by `LOGIN_ALLOWED_DOMAINS`, so the list doesn't accumulate redundant entries. **Additive only by construction:** the module has no removal/override path for the hardcoded list, only extension.

  **Global, not per-profile:** `baseUserDataPath` is captured at the very top of `main.js`, before any `--profile` remapping of `app.getPath('userData')` — this is a one-time machine-level trust decision, not account data, so every profile shares one file and a domain only needs whitelisting once regardless of how many profiles are in use. Confirmed directly: adding a domain with no `--profile` flag, then running `--profile=damon.downing --whitelist-list`, showed the same entry.

  CLI actions (`--whitelist-add=<domain>`, `--whitelist-remove=<domain>`, `--whitelist-list`) are one-shot: run, print a result, exit immediately without launching the app — same pattern as `--reset-aumid` above. Also added: `[Security] Allowed navigation to <host> (user-whitelisted via "<entry>")`, logged only when an allow specifically came from the user list rather than the hardcoded one, so a whitelist entry's effect is auditable from terminal output alone, not just inferred from the absence of a block.

  Tested live against the real command line, not just read through: add (exact and wildcard), add-of-an-already-hardcoded-domain (correctly declined with an explanation, not silently accepted), add-with-invalid-input (`not**valid`, correctly rejected with a reason), list (built-in and user-added shown separately, sorted), remove (both a real entry and a nonexistent one, correct behavior each time), and cross-profile sharing as above. Full login-flow-through-WorkOS itself not yet tested end-to-end (would need an actual WorkOS-backed org to sign into) — the navigation-allow logic is verified, but the complete real-world SSO round-trip is not.

- **Force session/weekly meter to 100% on active credit spend:** the reported `five_hour`/`seven_day` utilization percentage can lag behind reality near the plan limit — a session can already be actively billing to usage credits while the API still reports something like 98%. Since credit spend costs real money, waiting for the percentage to eventually catch up risks the user not realizing they're spending until they've already run up a charge. No single API field means "spending credits right now" — `extra_usage`/`spend` fields are monthly-cumulative totals, not a per-request flag (confirmed by comparing multiple live API responses, and by inspecting the official claude.ai frontend's own network requests, which hit the same endpoint this app already polls — no separate endpoint or flag explains its "Now using credits" banner timing).

  New module `src/detect-active-credit-spend.js` (same pattern as the existing `normalize-usage-limits.js`): compares `extra_usage.used_cents` against its value from the previous poll. If it increased while the relevant meter is already **≥95%**, forces that meter's utilization to 100 and sets a `credit_spend_forced` flag on it (not currently consumed by the UI — no visual distinction from a genuinely-reported 100% was wanted). The ≥95% gate specifically guards against a false trigger on a teammate's spend on a shared org account: `extra_usage`/`spend` are org-scoped, not per-user, so a rising total alone doesn't prove *this* session should jump — only a rising total **and** an already-near-ceiling percentage together do.

  Wired into the `fetch-usage-data` handler, after `storeUsageHistory()` — the history graph keeps the true reported percentages; only the live display and tray icons (both of which read `five_hour`/`seven_day.utilization` directly, confirmed via grep, so no renderer changes were needed) get the correction. The previous-poll comparison value is stored per-organization, matching the existing usage-history key-scoping convention.

  Tested two ways: (1) a standalone pure-function script covering 8 scenarios (first-poll safety, the 95% boundary inclusive/exclusive, session and weekly independently, the disabled-extra-usage case, the teammate-spend false-positive guard) — all passing; (2) a temporary `MOCK_CREDIT_SPEND_TEST=1` env-var hook exercising the real end-to-end pipeline (real IPC handler, real renderer, real progress bar) with two canned sequential API responses simulating the exact bug scenario. Confirmed working live, then the mock hook was committed and immediately reverted in the same branch, so the test is documented in history without shipping any test scaffolding.

- **Second (weekly) system tray icon missing on Linux/Wayland (Issue #119):** @williamvdev reported only the weekly stat showing in the tray on Fedora 44 KDE Plasma after upgrading to v1.7.6, with v1.7.5 showing both. Root cause fully identified via a real Fedora 44 KDE Plasma VM (built specifically for this investigation, native Wayland session confirmed via `plasmashell`/`loginctl` — an earlier attempt hand-layering KDE onto a GNOME-edition ISO produced a broken hybrid environment and was scrapped in favor of the real KDE spin) and a manual Electron version bisection.

  **Not our own code.** `createTray()`'s actual tray-creation logic was confirmed essentially unchanged between v1.7.5 and v1.7.6 — the only diff in that function was unrelated click-handler behavior. Bisecting Electron itself (holding app code at v1.7.6, only changing the pinned Electron version) found the exact boundary: **37.10.3 shows both icons, 38.8.6 shows only one.** That matches Electron's own changelog precisely — Electron 38.0.0 changed the *default* Ozone platform from Xwayland compatibility mode to native Wayland when launched in a Wayland session.

  **The actual mechanism, confirmed via Electron's own current docs** (`docs/api/tray.md`): *"If StatusNotifierItem is available, the first tray icon created will use SNI, while subsequently-created icons will use GtkStatusIcon."* This is documented, intentional behavior, not a bug we're triggering by misuse — but `GtkStatusIcon` is an older, X11-era protocol with no working implementation under native Wayland (it depends on X11 window-server semantics Wayland doesn't provide, the same category of gap as the legacy XEmbed tray protocol). Before Electron 38, every session quietly ran through Xwayland regardless of actual session type, so this fallback always had something to attach to and the gap never surfaced. Electron 38 stopped doing that by default — so this isn't really "Electron broke tray icons," it's "a documented fallback's Wayland gap stopped being silently papered over."

  Confirmed directly: `busctl --user introspect org.kde.StatusNotifierWatcher /StatusNotifierWatcher` showed only one registered `claude-usage-widget` item under native Wayland on 41.x; launching with `--ozone-platform=x11` (forcing Xwayland) restored both, confirmed via the same `busctl` check plus visual confirmation, on the same Electron version, same app code — isolating the fix to exactly this one flag.

  **Fix, two attempts — the first shipped briefly and made things worse:**

  *Attempt 1 (reverted same day):* `app.commandLine.appendSwitch('ozone-platform', 'x11')` as `main.js`'s first executable statement. Technically the earliest point in the JS layer, but that's still too late — Chromium's native Ozone/platform-backend selection happens in C++ before Electron hands control to this script at all. Live testing on the real Fedora VM showed this landed in a broken half-X11/half-Wayland hybrid state: `XGetWindowAttributes` failures, **zero** tray icons (worse than the original one-icon bug), not the clean Xwayland mode a genuine command-line argument produces.

  *Attempt 2 (shipped):* a one-time self-relaunch instead — `app.relaunch({ args: process.argv.slice(1).concat(['--ozone-platform=x11']) })` followed by `app.exit(0)`, guarded so it only fires once (checks whether `--ozone-platform=x11` is already in `process.argv` before relaunching, preventing an infinite loop). A real command-line argument, present in the new process's `argv` from the moment it starts, is parsed early enough to genuinely take effect. Confirmed live on the same Fedora 44 KDE Plasma Wayland session: clean single relaunch (visible as a brief restart at startup), both tray icons render correctly, `busctl` confirms both registered.

  Both attempts guarded identically: `process.platform === 'linux' && process.env.XDG_SESSION_TYPE === 'wayland'` only. X11 sessions, Windows, and macOS are completely untouched — confirmed no code path executes on Windows via manual launch/log inspection, both times.

  **Known open question, explicitly out of scope for this fix:** ad hoc testing against Electron 43.4.1 (well outside this app's `^41.10.1` pin — not reachable without someone deliberately editing `package.json`) showed **zero** tray items registering at all, with or without the compat flag — a different and more severe symptom than the 38–41 range, root cause not identified. Three untested theories: the compat flag itself may have weakened further in 42/43; a separate, unrelated Linux tray regression may have landed since 41; or this VM's GTK/`libdbusmenu`/`libappindicator` versions may simply predate what Electron 43 expects. **Do not bump Electron past the 41.x line without first re-testing both system tray icons on a real Linux/Wayland session** — this is not covered by any existing automated check, and the exact same "looks fine, only breaks Linux" pattern is what let the original v1.7.6 regression ship unnoticed in the first place.

  **Broader lesson worth carrying forward:** two separate Linux tray/taskbar-identity bugs now, on two different subsystems (this one, and the earlier Windows AUMID-corruption saga), both root-caused only by hands-on testing on the real target platform — neither was catchable by code review alone. Linux tray-icon behavior specifically needs deliberate manual verification on every Electron version bump going forward, not just a "did it start without crashing" smoke test.

  Filing an upstream Electron issue is planned but not yet done — the accurate framing is a documented-behavior gap (`GtkStatusIcon` fallback doesn't function under native Wayland, with no indication of that in the docs), not a regression report, since Electron never actually promised multi-instance `Tray()` parity.

- **Session key decryption fallback — fixes silent logout, consolidates duplicated code (PR #110):** @adihebbalae reported that three call sites (`get-credentials`, `fetch-usage-data`, and startup) each had identical inline DPAPI decryption logic, with the same real gap in all three: when `safeStorage.isEncryptionAvailable()` is true but `sessionKey_encrypted` doesn't exist — because the key was saved back when encryption wasn't available and landed in the legacy plain `sessionKey` field instead — none of the three checked that legacy field. The session key stayed `null` and the user was silently logged out to 0% / "Not started" with no indication why.

  New `getStoredSessionKey()` helper, shared by all three call sites, replacing the duplicated blocks. Adopted PR #110's legacy-plaintext fallback as-is (a real, valid key just stored under the old scheme). Changed one piece after review: the PR's original catch-block behavior on a genuine decryption failure (corrupted/unreadable ciphertext — DPAPI key changed after an OS reinstall, a config folder copied to a different machine, etc.) returned the raw ciphertext as a fallback "session key." There's no plain-text key hiding in that case — that's already handled by the legacy-field branch — so returning ciphertext just changes what the failure looks like (fails against the API instead of cleanly prompting re-login) without fixing anything. Changed to: clear the corrupted `sessionKey_encrypted` entry and return `null`, which already correctly routes to the existing login screen, and also stops the same corrupted entry from failing to decrypt on every future read.

  Tested both edge cases directly against a running instance, not just by reading the code: a PowerShell harness wrote a minimal store file into two dedicated test profiles (legacy plain-text key present, and corrupted/garbage ciphertext present) and launched the real app against each, with temporary diagnostic logging (committed, verified, then reverted in the same branch) confirming which branch fired. Legacy-plaintext case: key was found and actually used in a real network attempt (confirmed by a clean API-side validation error using the fake test organization ID, proving the key reached the real fetch path, not just detected and dropped). Corrupted-ciphertext case: decryption genuinely failed (confirmed via the real DPAPI error message, not a false trigger), the entry was cleared, and — critically — `sessionKey_encrypted` was verified completely absent from the store file *after* launch, confirming the cleanup actually persisted to disk rather than just being logged.

- **Retry with backoff on 429, RateLimited/SessionExpired classification, jittered auto-refresh (PR #114):** @mtspl reported that a single transient 429 from Claude.ai's edge was treated identically to a Cloudflare challenge or an expired cookie — sessionKey and organizationId were deleted and the user was forced through a manual re-login (itself involving a Cloudflare wall) for what might just be a momentary rate limit, e.g. right after a laptop wakes from sleep and several widget instances (or other Claude.ai tabs) poll at once.

  Three pieces, adopted from the PR with one addition dropped and one real bug found and fixed before merging:
  - **Retry with exponential backoff** (`src/fetch-via-window.js`, `main.js`): rate-limit responses are retried — 1 initial attempt plus up to 3 retries (4 attempts total), with 1s/5s/30s base delays and ±25% jitter. Session-bound errors (Cloudflare challenge, expired cookie, unexpected HTML) are never retried. Adopted as submitted; the logic was correct.
  - **RateLimited classified separately from SessionExpired**: a new `RateLimited` error prefix, checked before the block signatures, so a retry-exhausted rate limit keeps the session intact instead of forcing re-login. **Not adopted from the original PR:** an `Unauthorized` (401) matcher was dropped — this app never inspects HTTP status codes anywhere; it loads pages in a hidden `BrowserWindow` and reads `document.body.innerText`, so there is no code path that could ever throw an `Unauthorized` error. Confirmed by grep against both `develop` and the original PR branch before dropping it, rather than keeping unreachable dead code with a justification that didn't match how the fetch layer actually works.
  - **Jittered auto-refresh interval** (`src/renderer/app.js`): `setInterval` replaced with a self-rescheduling `setTimeout` at the configured interval ±25%, with the next tick scheduled only after the current fetch settles (so an in-flight 429 retry chain can never overlap with the next auto-refresh). **Real bug found and fixed before merging** (not present in the shipped version): the original PR's internal timer cleanup reused `stopAutoUpdate()`, which also sets a `_autoUpdateStopped` flag as a side effect — nothing ever reset that flag back to `false` before the recursive reschedule check ran, so auto-refresh fired exactly once after `startAutoUpdate()` and then silently died for the rest of the session, deterministically, every time. Fixed by having the internal reschedule clear its own pending timer directly, without touching the stop flag — only the real external start/stop calls touch it now.

  Tested all three pieces directly against a running instance. Auto-refresh scheduling: a 15-second interval with a fake-but-usable legacy session key produced five consecutive successful reschedule cycles in the renderer console with no stall, plus visibly correct jitter (delays of 11.4–18.4s around the 15s base, matching the ±25% band). Retry/backoff: a temporary mock (env-var gated, committed and reverted in the same branch) shadowed the real fetch call inside the actual retry loop to exercise three scenarios end-to-end — recovery after 2 failed attempts (widget displayed the mock's distinct fake percentages, proving data reached the real pipeline, not just the log), exhausting all 4 attempts (session preserved, no forced login), and a session-bound block on the first call (exactly 1 attempt, no retries, immediate correct logout). All three matched expected behavior exactly, with backoff delays confirmed landing inside their jitter bands in the terminal output for every attempt.
